Setting Up the Test Suite

A test suite = group of related test cases (just like Sanity/Smoke/Regression grouping in manual testing).

📘 describe() — the Suite
  • High-level container for related tests
  • Cannot nest another describe() inside a test()
  • Can hold multiple test() blocks
🪝 Hooks
  • beforeEach — runs before every test
  • afterEach — runs after every test
  • beforeAll / afterAll — once per suite

Put repeated setup (open URL + verify loaded) inside beforeEach — DRY principle!

// Global constant — reused everywhere
const PAGE_URL = "https://.../autoplay.html";

test.describe('Data Entry Form Validation', () => {
  test.beforeEach(async ({ page }) => {
    await page.goto(PAGE_URL);
    await expect(page.getByText('AutoPlay'))
      .toBeVisible();
  });

  // individual test() blocks go here
});
⏸ page.waitForTimeout(ms)
Hard pause — like Thread.sleep() in Java. Only for dev/visibility, not a smart wait. Doesn't cause flakiness; simply pauses execution.
3

Test 1 — Page Load Validation Exam Fav ⭐

test('Page load validation', async ({ page }) => {
  await expect(page).toHaveURL(PAGE_URL);
  await expect(page.getByText('AutoPlay'))
    .toBeVisible();
});
🎯 Exam Trick — Why TWO assertions?

toHaveURL() only proves the address bar is correct — NOT that the page rendered! A 404/500 page can still show the "correct" URL.

Always pair it with an element-presence check (logo/heading text) → this is the real proof of successful load. Memory trick: "URL tells you WHERE, element tells you WHAT."

4-Step Checklist for ANY input box (works for text, email, phone, textarea):

& Enabled

Value

Value Entered
// Full Name
await expect(nameField).toBeVisible();
await expect(nameField).toBeEnabled();
await expect(nameField).toHaveAttribute('maxlength', '15');
await nameField.fill('John Kennedy');
await expect(nameField).toHaveValue('John Kennedy');

// Address — multiline using \n
await addressField.fill('123 XYZ Lane\nDelhi\nIndia');
await expect(addressField).toHaveValue('123 XYZ Lane\nDelhi\nIndia');
📝 .fill() = Playwright's sendKeys(). Returns a Promise → always await it. Auto-overwrites existing text.
🔢 Numbers must still be passed as strings: fill("9999999999")
↵ "\n" inside fill() string → creates a new line (multiline address/textarea)

🚨 THE Most Important Distinction

🎯 toHaveValue vs toHaveText Most Asked!
AssertionWhen to Use
toHaveValue()Value YOU entered at runtime (fill/type). Not baked into HTML. Use for ALL input/textarea fields.
toHaveText()Text predefined/static in the DOM (e.g. button's inner text, a heading)

Memory Trick 🧠: "If YOU typed it in → toHaveValue. If it was already sitting in the HTML → toHaveText."

<input> — has VALUE attribute
<input value="Submit">

Value = runtime-fillable content → toHaveValue

<button> — has INNER TEXT
<button>Submit</button>

Text between tags = static DOM content → toHaveText

⚠️ Common Mistake
Using toHaveText to verify something YOU filled in — it will fail/mismatch, because the DOM was never rebuilt with your dynamic input. Always default to toHaveValue for form fields.
7

Test 3 — Radio Button Validation

const maleRadio   = page.getByLabel('Male', { exact: true });
const femaleRadio = page.getByLabel('Female', { exact: true });

await expect(maleRadio).toBeVisible();
await expect(femaleRadio).toBeVisible();

await femaleRadio.check();

await expect(femaleRadio).toBeChecked();
await expect(maleRadio)..not.toBeChecked();
🎯 exact: true
Prevents partial-text collision — e.g. getByLabel('Male') could also match inside "Female" as a substring. Always use exact:true when labels overlap.
✅ .check() not .click()
Semantically correct for radios/checkboxes even though .click() may also work. Use the action that matches the element's purpose.
Element.check().uncheck()Multi-select?
Radio Button✓✗ (auto-unchecks sibling)✗ one at a time
Checkbox✓✓✓ multiple allowed
🌀 .not. — Universal Negation
Works with every assertion → .not.toBeChecked(), .not.toBeVisible(), .not.toHaveValue() etc.

🎯 Exam-Trick Boxes — Quick Fire

Q: Why beforeEach and not repeat code in every test?
A: DRY principle — beforeEach runs automatically before EVERY test() in the describe block, avoiding duplicate goto()/visibility checks.
Q: describe() inside test()?
A: Not allowed ✗. describe = suite (outer), test = case (inner). Suites can contain many tests, never the reverse.
Q: Can .check() replace .click() on a button?
A: No — .check() is only for checkbox/radio inputs. Buttons/links still use .click().
Q: Selenium equivalent of .fill()?
A: sendKeys(). Both simulate typing text into an input element.
